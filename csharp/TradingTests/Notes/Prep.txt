# Top K elements
---------------------
Top K Elements - interview problem breakdown
The problem usually means: given an array of size n, return the k largest (or smallest) elements.
Common variants: - Top K largest numbers
- Top K frequent elements
- Top K in a stream (online)
What is being tested
- Choosing the right data structure
- Time vs memory tradeoff
- Handling edge cases cleanly
- Understanding when full sorting is wasteful
Main approaches
- Full sort: O(n log n), simple, often not optimal when k << n
- Min heap of size k: O(n log k), standard interview answer
- Quickselect: average O(n), worst case O(n^2), good for one-shot selection
- Bucket/counting methods: near O(n) when value/frequency range is bounded
Typical pitfalls
- Forgetting edge cases: k = 0, k > n, empty input
- Wrong heap type (min vs max)
- Returning unsorted top-k when sorted output is required
- Not defining behavior for duplicates
- Using O(n log n) sort when interviewer expects better
- For Top K frequent: forgetting tie handling rules
- For streaming: recomputing from scratch each update
C# angle (.NET)
- Use PriorityQueue<TElement, TPriority> for heap solution
- For high throughput, minimize allocations and avoid unnecessary LINQ in hot paths
- For stream scenarios, combine Dictionary<T, int> + bounded heap
Quick rule of thumb
If k is much smaller than n, heap is usually the safest interview choice.
If one-time query and no ordering requirement, quickselect is often fastest in practice.
